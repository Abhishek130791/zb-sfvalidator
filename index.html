The problem

A CRM full of addresses is not a CRM full of reachable people.

Leads arrive with typos, dead domains, generic inboxes, or no email at all. Sending to them burns sender reputation and hides real prospects. The job isn't just to flag the bad ones — it's to find the address that actually works.

How it works

Six stages, one webhook call.

A user selects records in Salesforce and picks an action. From there the whole run is automated — validation, discovery, and write-back — and every record exits with a stamped status.

01
Trigger
A list-view or record action in Salesforce fires a secured webhook. A shared secret header is checked before any work begins.
02
Fetch
The selected Lead and Contact records are pulled by ID over SOQL, with the fields the pipeline needs to validate and, if necessary, discover.
03
Validate
Existing addresses are checked through ZeroBounce using the batch endpoint — up to 100 per request — so call volume stays low and the provider's firewall never rate-limits the run.
04
Classify
Each result is sorted into one of six deliverability states, from clean Valid through Catch-all to Invalid.
05
Discover
For invalid or empty records, the pipeline resolves the related organisation, reads verified peer addresses at that domain, infers the naming pattern, and verifies one high-confidence guess.
06
Stamp
Status, detail, suggested email, and a validation timestamp are written back to every record in batches — including the ones that stay invalid, so nothing goes silent.
Architecture

Three systems, one contract between them.

Salesforce owns the data and the UI. n8n owns the orchestration. ZeroBounce is the deliverability oracle. Each does one job, and the boundaries are explicit.

Salesforce

System of record + UI
  • Custom fields for status, detail, suggested email & last-validated
  • Apex validation service & list controllers
  • LWC quick actions + Visualforce list-view buttons
  • Named Credential for the outbound callout
  • Permission Set scoping access to authorised users

n8n

Orchestration
  • Webhook trigger with secret-header check
  • SOQL fetch, batch assembler & response mapper
  • Classifier node routing the six states
  • Discovery branch: resolve → peers → infer → verify
  • Composite API write-back in batches of 200

ZeroBounce

Deliverability oracle
  • Batch validation of existing addresses
  • Single-address verification of inferred guesses
  • Catch-all and generic-domain signals
  • Used strictly as a filter — never as a generator
Classification

Every record lands in exactly one state.

The state is what downstream teams act on — it decides whether an address is used, replaced, or left alone. The colour language runs through the whole product.

Valid
Deliverable. Safe to use as-is.
Valid — Generic Domain
Deliverable, but a free provider (gmail, yahoo) — flagged for context.
Valid — Domain Mismatch
Deliverable, but the domain doesn't match the account's website.
Catch-all — Unverified
Domain accepts everything; the mailbox can't be individually confirmed.
Invalid — No Email Found
Undeliverable, and discovery couldn't recover an address.
Invalid — Suggestion Failed
Undeliverable; a candidate was inferred but didn't verify.
Engineering decisions

The choices that made it work in production.

The hard parts weren't the API calls — they were cost, rate limits, and making sure no record ever disappeared.

Infer before you validate

ZeroBounce is a filter, not a generator. Submitting one high-probability inferred candidate matches or beats a pile of brute-forced permutations — at a fraction of the API volume.

Batch, don't hammer

Rapid sequential calls trip the provider's firewall (Cloudflare 1020). The batch endpoint collapses call volume into a single request and keeps the run clean.

Cache the pattern per domain

Once a company's naming convention is confirmed, it's reused for future records at the same domain — no repeat validation calls to relearn what's already known.

No silent drops

Every record that enters the workflow exits with a stamped status — including the definitively invalid ones. Silent skips create invisible problem records, the hardest kind to find later.

Handle catch-all honestly

When a domain accepts every address, mailbox-level confirmation is impossible. The record is labelled for what it is, and inferred pattern confidence becomes the only decision signal.
